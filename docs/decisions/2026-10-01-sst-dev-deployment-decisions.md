# SST dev deployment: implementation decisions

**Date:** 2026-10-01

The interchangeable choices made while building the first deployment. Each
could have gone another way at no cost to a user or a recorded decision;
changing one is an ordinary change. Owner-level questions are not here: they
are review-batch items.

| #   | Choice                                                                                       | Why                                                                                                              |
| --- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| S1  | The SST app lives in a new workspace package, `deploy/`                                       | `infra/` is the platform; one SST app spans frontend and backend, which share one distribution                   |
| S2  | The API deploys the bundle `pnpm build` makes (`backend/dist`), not one SST bundles itself    | the artifact the bundle tests checked is the one deployed                      |
| S3  | The site is built inside the deploy (a Pulumi command), as SST's own sites are               | `SITE_URL` is the distribution's address, known only after it exists                                             |
| S4  | Site files are uploaded with `aws s3 sync`, not one Pulumi resource per file                  | faster deploys, readable diffs; without `--delete`, hashed files of the previous build stay for open tabs         |
| S5  | `/*` is invalidated after each deploy                                                         | one invalidation path; SST 4.17.1's router `invalidation` option is documented but not implemented               |
| S6  | OpenNext's tag cache and revalidation queue are off (`dummy`)                                 | nothing uses ISR or `revalidateTag`; the queue's consumer would poll, billed, while idle                         |
| S7  | Memory: API 1024 MB, site server 1536 MB; timeouts 20 s; every Lambda arm64                   | D4's "about 1.5 GB"; 20 s is CloudFront's origin read timeout                                                    |
| S8  | Tags `<project>:app` and `<project>:stage` through the provider's `defaultTags`                 | beside SST's own `sst:app`/`sst:stage`; one key per meaning that SST cannot rename                               |
| S9  | Basic auth user `<project>`, password 32 random letters and digits, one value for every dev-account stage (`--fallback`) | one credential for the owner to keep; throwaway stages need no setup                         |
| S10 | The visitor's address is written by the viewer-request function as `cloudfront-viewer-address`, `<ip>:0` | the API reads that header in CloudFront's `ip:port` form; CloudFront's own header cannot be forwarded to API Gateway |
| S11 | `/media/*` uses AWS's managed CachingOptimized policy, compression off                       | media need no query string or header in the key, and WebP/JPEG do not compress further                          |
| S13 | `CdnLogs` keeps logs 90 days                                                                  | enough for a month's cost report with margin; logs hold visitor IPs, so not longer                               |
| S14 | The image loader returns the URL unchanged                                                   | the backend makes every size (O16); the loader only keeps Next's optimiser out (D4)                              |
| S16 | A request without the origin secret gets `403` on every path, `/api/health` included: the API's `forbidden` error body, the site's plain `Forbidden` | a caller learns no more from `403` than from `404`; it tells a refusal apart from an unknown route in the logs and the smoke test; nothing needs health at an origin (CloudFront serves it) |
| S17 | The site's check is Next's proxy (`frontend/src/proxy.ts`), now run on every path, not a wrapper around OpenNext's server entry | app code, unit-tested, and it runs under `next start` too; OpenNext runs the proxy before its page cache, so prerendered pages are covered (the smoke test proves it) |
| S18 | The smoke test checks each API Gateway address three ways: no secret and a wrong one (`403`), the right one (`200`) | the third tells the refusal apart from a broken origin; the secret travels only to the stage's own addresses and is never printed |
| S19 | The visitor's address reaching the API was confirmed once on `dev` (2026-10-06) by reading the `LOOKUPFAIL#` counter after failed lookups, not by a smoke check | a smoke check would need table access and this machine's public address on every run; the counter is the address's only consumer, so reading it once proves the path |
| S20 | The viewer-request function's whole code, SST's router and our injection, is compacted with terser before CloudFront gets it (`compactFunctionCode` in `deploy/src/edge.ts`, through the `aws.cloudfront.Function` transform in `sst.config.ts`): local names shortened, whitespace gone, `handler` and `cf` kept, no newer syntax written (ecma 5). `deploy/src/edge-function.test.ts` rebuilds the function from SST's own source for every stage, holds each to 9,216 bytes (CloudFront's 10,240 less 1 KB) and runs the written and compacted versions against the same requests, every gate included (2026-10-19) | Dev's function measured 9,854 of 10,240 bytes, 8,625 of them SST's router, which SST hands over unminified; our injection was 1,229. Compacted: dev 6,804, production 6,607, dev once on its domain 7,053 (10,159 uncompacted, over the limit). Shrinking our injection could win at most its 1,229 bytes; moving rules or secrets to the router's KeyValueStore adds a read per request, billed, and a secret in its data; Lambda@Edge or origin checks would move a gate after the cache. Compacting costs nothing at run time and weakens no gate |
| S22 | Every answer of the distribution carries one CloudFront response headers policy of our own, `<project>-<stage>-security` (`securityHeaders` in `deploy/src/cdn.ts`, on the router's default behaviour and on `/media/*`; the media policy holds the same headers): `Strict-Transport-Security: max-age=63072000; includeSubDomains` (no preload yet), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` (yielding to an origin's own header; a page's own `no-referrer` meta is stricter and wins in the browser). The site sets `poweredByHeader: false`. No CSP yet (2026-10-21) | A security check found no security header on production or dev. includeSubDomains is safe while every name under the project's domain that answers HTTP is a CloudFront distribution redirecting to HTTPS (the apex, www's redirect, `dev.<domain>`), `auth.*` is Cognito's HTTPS-only domain when made, and the mail names hold DNS records only; any future subdomain must be HTTPS-only. No page is meant to be framed (embedded widgets frame their own pages inside ours, not ours elsewhere). Our own policy rather than AWS's managed SecurityHeadersPolicy, whose HSTS is one year without includeSubDomains and whose `X-Frame-Options` is SAMEORIGIN. A policy costs nothing; preload waits until the domain's setup is final, since leaving the preload list takes months |
